# 커스텀 Chrome 확장 구현·테스트 가이드

Side panel 모드와 GitHub Release 기반 내부 파일 업데이트를 구현했다. 브라우저 E2E는 사용자가 실행한다. 단위 테스트의 메모리 파일 시스템 검증과 실제 Chrome의 설치 폴더 접근·네이티브 패널 동작은 별도 검증이다.

## 로컬 자동 검증

저장소 루트에서 실행한다. 저장소의 `.nvmrc`에 맞는 Node를 사용한다.

```bash
npm ci
npm run test:custom-updates --workspace @bitwarden/browser
npx jest --config apps/browser/jest.config.js --maxWorkers=2
npx ngc --noEmit -p apps/browser/tsconfig.json
npx tsc --noEmit -p e2e/tsconfig.json
npm run build:prod:chrome --workspace @bitwarden/browser
```

`test:custom-updates`는 Node 패키징 테스트와 Jest 계약·파일 적용·소스 조회·패널 중계·업데이트 화면 준비 테스트를 실행한다. 전체 ZIP과 패치 ZIP의 재구성 결과를 비교하며, 실제 GitHub 배포나 Chrome 실행은 하지 않는다.

주요 자동 테스트는 숫자 버전 정렬, 잘못된 경로·ZIP·해시 거부, 변경/추가/삭제와 Manifest 마지막 반영, 기준 파일 변조·추가 감지, 권한 거부, 쓰기·삭제 실패 복구, 백업 저장 실패 시 무변경, 창별 요청 분리, 만료·취소, 모드 저장 실패 복원, 편집·인증 중 업데이트 보류를 다룬다.

## CI/CD 최초 설정

대상은 공개 GitHub 저장소의 압축해제 Chrome MV3 빌드다. 런타임에 GitHub 토큰을 포함하지 않는다. 기존 공식 배포 워크플로와 별도인 커스텀 워크플로를 사용한다.

1. `main`에 확장 관련 변경을 푸시하면 `Custom Chrome Extension`이 자동 실행된다. 현재 소스 버전과 이미 사용한 릴리스 버전보다 높은 숫자 버전을 자동으로 정한다. Actions의 **Run workflow**에서 `version`을 비워도 같은 방식으로 실행한다. 직접 지정하려면 `2026.11.0.1` 같은 숫자 버전을 입력하거나 `browser-custom-v2026.11.0.1` 태그를 푸시한다. **업데이트용 키·Secret 등록은 필요 없다.**
2. 워크플로는 패키징 테스트와 브라우저 전체 단위 테스트를 실행한다. 이전 릴리스의 버전·전체 빌드를 확인하고 프로덕션 빌드 후 버전·저장소 설정을 주입한다. 최종 파일 해시를 비교해 전체 ZIP, 변경 파일 ZIP, 삭제 계획, 메타데이터를 생성한다. 패치 재구성을 검사한 후 모든 자산을 Draft Release에 업로드하고 공개한다. 최초 릴리스에는 기준 패치가 없다.
3. 다음 배포에는 버전만 증가시킨다. 직전 버전의 파일 목록 해시와 일치하면 델타를 받고, 버전을 건너뛰면 전체 ZIP으로 차이를 계산한다. 두 경우 모두 실제로 바뀐 파일만 쓰고 제거된 파일을 삭제한다.

설치 파일은 [최신 Release](https://github.com/whitenight209/bitwarden-clients/releases/latest)의 `extension-chrome-custom-VERSION.zip`이다. Actions 실행의 Artifacts에서도 `chrome-extension-VERSION`을 받을 수 있다. 아티팩트의 바깥 ZIP을 풀면 여러 배포 파일이 나오므로 그 안의 설치 ZIP을 한 번 더 풀어 사용한다. 실행 결과 Summary에도 다운로드 링크와 설치 방법이 표시된다.

새 버전은 현재 버전과 Release의 숫자 버전으로 판단한다. 서명 파일은 만들거나 검증하지 않는다. 파일 해시는 변경 파일 계산과 다운로드 오류 확인에 사용한다. Manifest의 기존 설치 식별값은 유지하며 별도 공개키를 설정하지 않는다.

## 최초 설치와 업데이트

1. Release의 `extension-chrome-custom-VERSION.zip`을 고정 폴더에 압축해제한다. macOS 예시는 `~/ChromeExtensions/Bitwarden`이며 `manifest.json`이 바로 보이는 디렉터리를 사용한다. **`/Applications`, `~/Applications`와 그 하위 폴더에는 설치하지 않는다.** Chrome의 파일 접근 API가 이 경로를 차단하므로 내부 업데이트용 폴더 연결을 할 수 없다. [Chromium의 macOS 차단 경로](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/file_system_access/chrome_file_system_access_permission_context.cc)
2. `chrome://extensions`에서 개발자 모드를 켜고 해당 폴더를 로드한다.
3. 로그인 후 설정 → 화면 스타일 → 커스텀 확장 업데이트에서 **설치된 동일 폴더**를 선택하고 쓰기 권한을 허용한다. Manifest·버전·전체 파일 해시가 맞아야 연결된다. 같은 내용의 복사 폴더와 실제 로드된 폴더를 API로 구분할 수 없으므로 실제 설치 폴더를 선택해야 한다.
4. 잠금 해제 완료 후 마지막 성공한 확인에서 24시간이 지났으면 새 버전을 비동기로 확인한다. 팝업·패널 열기나 worker의 기존 키 복원은 조회하지 않는다. 새 버전은 배너로 안내하고 업데이트 적용 버튼을 눌렀을 때만 다운로드·설치한다. 주기 알람과 자동 적용 옵션은 없다.
5. 다음 릴리스를 배포하고 내부 확인 → 새 버전 안내 → 업데이트 적용 클릭 → 다운로드·파일 확인 → 변경 파일 적용 → 재로드 → 새 버전 부팅 검증까지 확인한다. 브라우저 저장소의 계정·보관함은 업데이트 파일 목록에 포함되지 않는다.

폴더 권한이 만료되면 같은 폴더를 다시 선택한다. 중단 저널이 남아 있으면 복원을 완료하기 전 폴더를 교체할 수 없다. 이때 동일 폴더를 다시 선택해 권한을 허용한 뒤 **이전 파일 복원**을 실행한다. 복구가 불가능한 경우 Chrome에서 확장을 삭제하지 말고, 기존 설치 폴더에 정상 전체 ZIP을 복원하고 확장을 다시 로드한다.

일반 `build:prod:chrome`만 실행한 빌드는 업데이트 저장소 설정이 없어 업데이트 화면에 미설정 상태가 표시된다. 반드시 커스텀 패키징을 거친 Release ZIP으로 파일 업데이트를 검증한다. Web Store/CRX 설치는 대상이 아니다.

### 이미 Applications 아래에 설치한 경우

현재 공개 빌드는 새 경로에서 로드하면 경로 기반 확장 ID가 바뀐다. 기존 Chrome 저장소가 새 설치본으로 자동 이전되는 것으로 안내하지 않는다. [Chromium의 경로 기반 ID 생성](https://chromium.googlesource.com/chromium/src/+/main/components/crx_file/id_util.cc)

1. 기존 확장과 설치 폴더는 삭제하지 않는다. `chrome://extensions`에서 기존 확장을 비활성화하여 기존 저장소를 남겨 둔다.
2. 현재 설치 폴더의 **내용 전체를 그대로** `~/ChromeExtensions/Bitwarden`으로 복사한다. 새 폴더 최상위에 `manifest.json`과 `custom-update-installed.json`이 있어야 한다.
3. Chrome에서 **압축해제된 확장 프로그램 로드**로 새 폴더를 로드한다. 새 설치본에서 로그인하고 사이드 패널 등 로컬 설정을 다시 적용한다.
4. 새 설치본의 업데이트 화면에서 **방금 Chrome에 로드한 새 폴더**를 연결한다. 복사 폴더만 연결하고 기존 Applications 설치본을 계속 사용하면 안 된다.
5. **버전 확인 → 업데이트 적용**으로 검사한다. 이전 버전의 폴더를 그대로 복사했으므로 새 위치에서도 다음 버전으로의 내부 업데이트를 검증할 수 있다. 이후 이 경로를 고정해 사용한다.

## Playwright E2E

[side-panel-mode.e2e.ts](../e2e/tests/browser/side-panel/side-panel-mode.e2e.ts)에 12개 케이스를 추가했다. ON/OFF, 확장 재로드 후 설정 유지, 실제 `SIDE_PANEL` 문맥, 내부 경로 이동, 두 창 격리, 패널 열기 대기, 일반 빌드의 업데이트 미설정을 다룬다. 계정 잠금·재로드 이후 패널 복구와 입력 필드의 실제 잠금해제 버튼에서 시작하는 ON/OFF 회귀 케이스를 포함한다. [CDP 도우미](../e2e/src/browser/side-panel.ts)는 실제 네이티브 패널에 연결하며, [인라인 메뉴 도우미](../e2e/src/browser/inline-menu.ts)는 닫힌 Shadow DOM 안의 실제 버튼에 신뢰된 마우스 이벤트를 보낸다.

기존 [E2E README](../e2e/README.md)에 따라 테스트 전용 계정·서버를 준비한다. 계정 값은 `.debug/credentials.txt` 또는 `E2E_EMAIL`, `E2E_PASSWORD`, `E2E_SERVER`로 제공한다. 데스크톱 세션과 확장 로드를 지원하는 Playwright Chromium이 필요하다.

```bash
npm run build:prod:chrome --workspace @bitwarden/browser
npm run test:browser --workspace @bitwarden/e2e -- tests/browser/side-panel/side-panel-mode.e2e.ts
```

이 E2E는 작성·타입 검사 대상이며 이번 작업에서 브라우저로 실행하지 않았다. 실제 폴더 선택·설치 폴더 쓰기와 업데이트 재로드는 아래 시나리오로 추가 검증한다.

## 창 진입점 점검표

개별 기능의 창 열기 코드와 최종 브라우저 API 경계를 함께 확인한다. 외부 사이트·SSO 제공자·OS 인증·파일 선택 화면은 해당 플랫폼 화면을 사용한다.

| 진입점                                      | 공통 처리와 회귀 검증                                                                                        |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 아이콘·일반 팝업·인증 요청 알림             | `SidePanelMode`가 전역 패널·action 설정을 단독 관리. 잠금·재시작 후 활성 상태 유지                           |
| 입력 필드 잠금해제·상세·추가                | 검증된 iframe 메시지를 worker로 직접 전달. 포트 문서·프레임·탭·nonce 확인 후 비동기 처리 전에 패널 열기 시작 |
| 자동 채우기 단축키·우클릭                   | 잠금 상태를 구독해 사용자 이벤트 시점에 패널 열기 시작. 기존 재시도 명령과 요청 탭 유지                      |
| 항목 추가·편집                              | 기존 팝업 검색·재사용 전에 공통 패널로 라우팅                                                                |
| 로그인·2FA·SSO 결과·패스키·HTTP 인증·재인증 | 공통 `openPopout` → 패널 요청 중계. 문서 소유 검증·취소·만료 유지                                            |
| 확장 화면 탭·직접 창 생성                   | `BrowserApi.createNewTab/createWindow`에서 자체 UI URL을 판별하여 모드 적용                                  |
| 진단·Webmapper                              | ON에서는 공통 패널 사용. 화면 종료가 주 패널을 비활성화하지 않음                                             |
| 외부 사이트 열기·도움말·외부 SSO            | 기존 탭·플랫폼 동작 유지                                                                                     |

SP34는 아이콘으로 먼저 패널을 열어두거나 콘솔에서 `setOptions`를 실행하면 결함이 가려질 수 있다. 반드시 수정 빌드에서 잠금 후 패널을 닫은 채 실제 웹 입력 필드의 버튼으로 시작한다. ON/OFF 모두 계정 잠금·해제, 보관함 CRUD·검색·복사, 자동 채우기·저장, 생성기·Send·폴더, 가져오기·첨부, 인증·계정 전환을 반복한다. 네이티브 E2E 통과 전에는 이 전체 시나리오가 실제 Chrome에서 통과했다고 판단하지 않는다.

SP44·SP45는 패널의 `document.activeElement`뿐 아니라 `document.hasFocus()`도 확인한다. 기존 인라인 잠금해제 E2E에 두 검증을 포함한다. 포커스는 명시적인 잠금해제 요청에만 적용한다. Angular 경로 이동이 끝나도 입력란 생성·활성화·레이아웃과 브라우저의 키보드 포커스 전달이 늦을 수 있으므로 DOM 변경과 렌더링 프레임을 기준으로 기다린다. 30초는 포커스를 주기 위한 지연 시간이 아니라, 화면이 끝내 준비되지 않았을 때 대기·리스너를 정리하는 상한이다. 백그라운드 주기 작업은 추가하지 않는다.

새 배포를 내부 업데이트로 확인할 때는 **커스텀 확장 업데이트 → 버전 확인 → 업데이트 적용**을 사용한다. 수동 확인은 잠금해제 시의 24시간 제한을 우회한다. 적용 후 버전과 연결 폴더·사이드 패널 설정이 유지되는지 확인하고 SP44·SP45를 반복한다.

## 검증 범위와 기록

2026-11-27 로컬 검증 기록:

- 패키징 Node 테스트 18개 통과.
- 브라우저 전체 Jest 296개 스위트, 5,974개 테스트와 스냅샷 19개 통과. 입력 필드 잠금해제 메시지·원래 탭 재시도, 창 생성 경계·모드 ON/OFF, 단축키·우클릭, 잠금·worker 복원, FIDO2 중복 등록 방지와 기존 인증·보관함·자동 채우기 기능을 포함한다.
- 업데이트 적용 시 문서별 준비 응답, 상시 업데이트 포트 제거, 재시도 큐 없는 잠금 해제 요청 완료, 저장된 핸들의 클릭 시점 권한 요청을 검증했다. IndexedDB 트랜잭션 구현을 사용하는 테스트로 백업 바이트 저장·정상 완료 후 삭제·정리 중단 시 복구 데이터 보존·파일 내용 없는 이력 보관을 확인했다. 실제 Chrome의 권한 창과 내부 업데이트 완료는 아직 검증하지 않았다.
- 재로드 후 권한 재허용으로 완료 검증을 재시도하는 경우와 정상 부팅 전에 백업 정리를 하지 않는 경우를 추가했다. 해당 정책 테스트 19개 통과.
- 변경 TypeScript·스크립트의 ESLint, 문서·템플릿 포맷 검사, 브라우저·E2E 타입 검사 통과.
- Chrome 프로덕션 빌드 성공. Sass 관련 경고와 번들 크기 경고가 출력됨.
- 실제 빌드 파일의 전체 패키징·델타 재구성 검사를 제공한다. 버전만 증가하면 Manifest만 패치에 포함되는지 확인한다.
- 키·서명 파일 없이 새 버전 선택·패키징·검증되는 자동 테스트를 포함한다.
- Playwright 케이스 12개 작성. 브라우저 E2E는 미실행. GitHub CI도 브라우저 전체 단위 테스트를 통과해야 빌드·배포하도록 변경했다.

실행 기록에는 OS·Chrome 버전, 확장 ID, 설치 버전과 목표 버전, 케이스 ID, 결과·오류를 남긴다. 로그·화면 자료에는 테스트 계정만 사용한다.

이번 변경의 자동 검증은 패키징·검증 계약과 코드 동작을 다룬다. 실제 Chrome에서 자기 설치 폴더에 쓰고 재로드할 수 있는지, 재시작 후 권한을 얼마나 유지하는지, 패널과 인증 UI가 실제로 연결되는지는 E2E 통과 후에 확정한다. 여러 파일의 교체가 운영체제 수준으로 원자적이지 않으며, 고장 난 업데이터가 항상 스스로 복구된다는 보장은 없다.
